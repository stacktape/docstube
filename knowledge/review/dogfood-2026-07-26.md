## Claim mix — the structural ceiling

| Class            | Count | Share | Checkable in 0.1.0?                                                          |
| ---------------- | ----- | ----- | ---------------------------------------------------------------------------- |
| `behavior`       | 147   | 55%   | **No, by design** (trust-model-v2 decision 3 — predicate verifiers are v1.x) |
| `code-structure` | 72    | 27%   | Yes in principle                                                             |
| `value`          | 48    | 18%   | Yes in principle                                                             |
| `intent-history` | 1     | <1%   | Only via a maintainer answer                                                 |

**This is the single most important number in the run.** Behavior claims are the majority of what
real documentation asserts, and they are unchecked by design until v1.x. Even with every fixable
cause below repaired, pages land around 25–40% checked. The green "Verified" badge as specified
(100% of ledger claims checked) will essentially never appear at 0.1.0.

That is a product decision, not an engineering one, and it is deliberately left open here:
either the badge threshold changes, or behavior verification moves into 0.1.0, or the launch
story leads with "every claim is checked **or visibly marked**" rather than with green badges.

## Root causes found (all three from real output, none reachable by tests)

### 1. Cited-value subscriptions were never resolved — FIXED

The `configuration` page emitted claims in perfect canonical form:

```
predicate: configFileNames.config is `docstube.yml`
quote:     "`configFileNames.config` is `docstube.yml`."
```

…and every one shipped unchecked. The subscription had fallen back to a whole-file content hash
instead of a `cited-value` subscription, leaving the verifier nothing to compare. Cause: proposing
a value subscription requires a **symbol hash** the writer usually does not have (1223 symbols; it
sees a subset). The data was never missing — `extractCitedValues` on that file returns
`configFileNames.config = "docstube.yml"` correctly.

Fix: the kernel resolves the value path itself against the fingerprint snapshot, exactly as it
already resolves evidence file/span rather than trusting writer-supplied locations.

### 2. Public names differ from implementation names — FIXED

The `cli-reference` page burned a full writer retry on errors like:

```
claim "c4" is SUBJECT-UNBOUND — its evidence points at the symbol "runGenerateCommand",
but the visible prose ("docstube generate generates docs from existing config") never names it
```

The prose is **correct**: the command is called `docstube generate`; `runGenerateCommand` is its
implementation. This mismatch is endemic to real docs — CLI commands, config keys, HTTP routes and
env vars all have public names that differ from internal identifiers. Failing the page for it is
wrong and expensive (a retry is a full writer call).

Fix: an unbindable subject drops the evidence and the claim ships **unchecked**, never failing the
page. The kernel declines to vouch rather than declining to publish. The binding rule itself is
unchanged — an unbound subject still may never mint evidence.

### 3. Shell instructions are executed as if they were tests — OPEN

Two snippet-exec failures cost the other retry:

```
code sample failed to execute: exit code 1 — bash: line 1: cd: docs-site: No such file or directory
code sample failed to execute: exit code 22 (curl)
```

The offending fences are reader instructions (`npx docstube wizard`, `cd docs-site && npm run
build`, a `curl` installer), not self-contained testable examples. Executing them proves nothing
and can be actively wrong (running `docstube generate` inside its own verifier). The writer did use
` ```text ` for one installer, so the distinction is learnable but unreliable.

Proposed: shell fences require explicit opt-**in** to execution rather than opt-out. Executable
verification stays the default for languages where a snippet is self-contained (js/ts/python);
a shell block in documentation is usually an instruction executed in the reader's environment,
and claiming to have "verified" it by running it here is not honest anyway.

## Also found

- **The codemap walked gitignored build output** (58 files: bundled CSS/JS from a nested app).
  Two consequences: build artifacts treated as documentation source, and — because unversioned
  reads mark a run dirty — **the complete badge was unreachable in any repo with a `dist/`**.
  Fixed in `a90c15f`: git's own allowlist decides what counts as source. 733→675 files walked,
  58→0 unversioned reads.
- **Manifest index and shards can disagree** (index listed 6 pages, 1 shard on disk) and stale
  pre-JSON `.yml` shards were never cleaned up. Fixed in `dac271a`: shards are pruned against the
  index on write, and an index that outruns its shards is a typed error.
- **Site emission produced one route for six pages** in the post-run tree. NOT yet diagnosed —
  observed while a concurrent agent was mutating the repo, so it may be tooling churn rather than
  a product defect. Artifacts snapshotted; re-examine on a quiet tree before drawing conclusions.

## Runs 2 and 3 — after the fixes

| Metric                            | Run 1 (baseline) | Run 2              | Run 3                |
| --------------------------------- | ---------------- | ------------------ | -------------------- |
| Checked                           | 2 / 268 (0.7%)   | 29 / 341 (8.5%)    | 50 / 291 (17.2%)     |
| **Checked, excluding `behavior`** | ~2 / 121 (1.7%)  | 29 / 169 (17%)     | **50 / 105 (47.6%)** |
| Attempts for 6 pages              | 8                | **6 (no retries)** | 9                    |
| Shards persisted                  | 1 of 6           | **6 of 6**         | 6 of 6               |
| Contradictions / false flags      | 0                | 0                  | 0                    |
| Cost                              | ~$30             | ~$20               | ~$30                 |

**The number that measures the machinery is "excluding behavior": 1.7% → 47.6%.** A replay
projection made before run 3 predicted 47.9%; the live run landed at 47.6%, so the verifiers
behave in production as they do on recorded data.

**The headline percentage is noisy for a reason worth knowing.** Run 3 scored _lower_ overall
(17.2% vs 23.8% projected) purely because its writers classified 64% of claims as `behavior`
versus 50% the run before — and the `github-action` page emitted 51 claims, _all_ of them
`behavior`, where the previous run produced a checkable mix. Since behavior is unchecked by
design, the badge number moves with a stylistic choice the model makes each run. Writer phrasing
discipline is therefore a real lever on the published number, not just verifier capability.

### What produced the gain

- **Kernel-resolved subjects** — the kernel derives a claim's subject from its own canonical text
  and looks it up (codemap for existence, fingerprint value prints for values) instead of relying
  on a symbol hash the writer usually does not have.
- **Schema-shape verifier** — `z.object({...})` field presence, optionality and literal defaults
  extracted statically (never evaluated), so `docstubeConfigSchema requires schemaVersion` and
  `agentsConfigSchema defaults maxRunUsd to 20` are decidable. +42 claims, the largest single win.
- **Degrade instead of fail** — unbindable subjects and underivable dependencies ship unchecked
  rather than failing the page. Run 2 needed zero retries as a result.

### Also fixed along the way

- Existence was being tested against the **fingerprint snapshot** rather than the codemap. Since
  `extractFingerprints` is an additive pack capability, every symbol from a pack without it
  (`lang-python`, `lang-java`, any third-party pack) would have been falsely reported as not
  existing in the source. Latent, and severe for the plugin story.
- `authoritativeFileHash` consulted only _unparsed_ files, so a whole-file dependency on any
  cleanly-parsed source resolved only if the page happened to have read it — 209 of 250 committed
  subscriptions were resolving by luck.
- A second **raw NUL byte** (in `anchor-ledger.ts`, a map-key delimiter) matching the one found in
  `generate.ts`. Both were runtime-correct and both made git render the whole file as "Binary
  files differ", hiding every diff. A repository-hygiene spec now fails on any raw NUL in a
  tracked text file.
